20 things I check before any app goes live

The pre-launch pass that keeps launch week quiet.

From the post on 2 Nov 2026

Launch week is rarely about the feature. It is about certificates, email, migrations, and the assumptions that only break under real traffic. This is the pass I run before any app goes live, whether I built it or I am signing it off.

The story in 5 steps

  1. Set the bar before the date moves

    Situation A fixed launch date is on the calendar and the product demo works on staging.

    Decision Decide whether the date serves learning or revenue, and what must be true on day one.

    Tradeoff A hard date focuses the team; a soft date avoids shipping known gaps.

    What I choose I keep the date but define a written go/no-go list. Anything not on the list is out of scope for day one.

    What happens in prod When something slips, we cut scope instead of skipping checks. Launch day stays boring on purpose.

  2. Domain and transport

    Situation Users bookmark both www and bare host, and old links still use http.

    Decision Pick one canonical host and enforce HTTPS everywhere.

    Tradeoff Strict redirects can break old marketing links if they are not mapped first.

    What I choose One canonical host, http to https, certificates on auto-renew with an expiry alert two weeks ahead.

    What happens in prod Mixed content and certificate surprises are the first support tickets I see after go-live when this is skipped.

    • letsencrypt.orgLet's Encrypt docs

  3. Secrets and access on the server

    Situation The UI hides admin actions and the API feels fine in manual testing.

    Decision Treat the browser as public and the API as the real gate.

    Tradeoff Server checks and rate limits add code; skipping them ships faster until someone scripts the endpoints.

    What I choose Rotate anything that ever lived in a frontend bundle, deny-by-default data rules tested as a second user, rate limits on auth flows.

    What happens in prod Credential stuffing and ID tampering show up as odd support tickets long before a formal incident.

    • owasp.orgOWASP ASVS
    • cheatsheetseries.owasp.orgHTTP Headers Cheat Sheet

  4. Money and email paths

    Situation Checkout works in test mode and password reset sends from the default provider domain.

    Decision Trust webhooks and DNS, not the success page.

    Tradeoff Webhook idempotency and SPF, DKIM, and DMARC take a week of calendar time.

    What I choose Verified payment webhooks, a real declined-card test, authenticated mail on the production From domain, reset tested in Gmail and Outlook.

    What happens in prod Paid users with app state stuck on pending and resets in spam are the classic day-two fires.

    • docs.stripe.comStripe webhooks
    • developers.google.comSEO starter guide

  5. Rollback and eyes on the system

    Situation The deploy pipeline is green and nobody is scheduled for the holiday weekend.

    Decision Name who gets paged and how to roll back in one step.

    Tradeoff On-call rotas cost attention; without them, the first outage waits for whoever checks Slack last.

    What I choose One-step rollback rehearsed, error tracking that pages a human, uptime on a path that logs in, 301 map if URLs changed.

    What happens in prod Quiet launch weeks correlate with boring checklists, not with luck.

Paste into your coding assistant 
Audit this project against the 20 items below. For each: pass / fail / not applicable, the file or setting that proves it, and the smallest fix. Don't change code until I confirm.

DOMAIN & HTTPS
1. HTTPS only. Every http:// URL 301s to https://.
2. www and the bare domain resolve to ONE canonical host.
3. Certificates auto-renew, and something alerts you 14 days before expiry.
SECRETS & ACCESS
4. No secret keys in the frontend bundle. Anything that ever shipped to a browser gets rotated.
5. Database access rules deny by default. Test them logged in as a second, ordinary user.
6. Rate limits on login, signup, password reset, OTP and contact forms.
HARDENING
7. Security headers: HSTS, nosniff, Referrer-Policy, frame-ancestors, and a CSP rolled out in Report-Only first.
8. Dependency audit is clean or triaged; the lockfile is committed.
DATA
9. Automated backups, plus one real restore into a scratch environment. Time it.
10. Every migration has a rollback, or a written roll-forward plan.
MONEY & EMAIL
11. Payment webhooks: signature verified, idempotent, safe to retry. App state comes from the webhook, not the success page.
12. A refund and a declined card tested end to end.
13. SPF, DKIM and DMARC on the domain you send from.
14. Password reset and verification emails tested in Gmail AND Outlook.
SEEING PROBLEMS
15. Error tracking that alerts a human, not a dashboard nobody opens.
16. Uptime check on a real path (log in, load data), not just the homepage.
17. Logs contain no passwords, tokens or personal data.
SEARCH & ROLLBACK
18. Titles, meta descriptions and OG image per page, sitemap.xml live, robots.txt not blocking production, staging noindex removed.
19. Replacing an old site? A 301 map from every old URL.
20. Rollback in one step, and a named person on call for the first 72 hours.

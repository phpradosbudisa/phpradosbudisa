4 docs before anyone touches your codebase

The 4 files that stop newcomers guessing.

Onboarding speed is documentation speed. Before a new hire or contractor merges, I want four short files that answer run, architecture, decisions, and rules.

The story in 3 steps

  1. Runbook before repo tour

    Situation A newcomer asks how to deploy in chat every week.

    Decision Write commands before explanations.

    Tradeoff Runbooks go stale if nobody owns them.

    What I choose RUNBOOK.md with local run, test, deploy, rollback, logs, and who gets paged.

    What happens in prod Tribal knowledge ships guesses; guesses ship bugs that the next person re-guesses.

  2. Architecture for money paths

    Situation Modules overlap and nobody knows which table owns billing state.

    Decision Document modules, owned tables, and the three journeys that pay.

    Tradeoff Architecture docs can balloon into unreadable wikis.

    What I choose One short ARCHITECTURE.md: modules, data flow for signup, core action, payment, external dependencies.

    What happens in prod Outages stretch when three people each think a different service owns the broken table.

    • cognitect.comDocumenting Architecture Decisions
    • adr.github.ioadr.github.io

  3. Decisions and rules

    Situation A smart newcomer refactors a deliberate tradeoff.

    Decision Record big choices and no-go zones.

    Tradeoff ADR overhead feels heavy on a two-person team.

    What I choose DECISIONS/ with context and consequences; RULES.md for naming, logging, migrations, billing, auth review.

    What happens in prod Without written decisions, every new contributor relitigates the same boundary calls.

    • cognitect.comDocumenting Architecture Decisions
    • docs.github.comSetting guidelines for repository contributors
